# Code review, 3acff4dd to 6b6439e1, 2026-10-20

Eight fixes landed on `review/2026-10-20`, one commit each with its test, and none changes a reply or a served kernel.
Three more need the GPU and sit in `tf-runs/review-1020/patches/` with `gpu-check.sh`. Four reviewers read the 72
commits, split four ways:

- GLM's decode switches.
- LFM2.5, d1, the server and the tools.
- The EXL3 kernels.
- The switch defaults, Flash Next's EXL3 matrices and the tests.

No high-severity bug turned up. The worst defect is a gap in `run.sh` that lets a direct load skip `run.lock`. The
CPU suite failed one test at 6b6439e1 because a child process imported the image's installed `tensorfold`. The fixed
branch passes all of it (numbers in the last section).

## Decision: off-by-default code measured neutral

**`TF_EXL3_EXPERT_DECODE` with `DECODE_TILES`: remove.** It served 0.99-1.00x on Qwen and 0.978-0.990x on GLM-5.3
(19 Oct). Each codebook builds 16 `decode_kernel` instances beside 22 `grouped_kernel` ones, 42% of the extension's
kernels.

| Kind | What goes |
|---|---|
| CUDA | `experts_grouped.cuh:438-621` (`decode_tiles`, `decode_kernel`) and `:720-745` (`decode_launch`), line 6 of `experts_cb0/1/2.cu`, `experts.cu:378-380, 423-433`, the `decode` argument in `experts.cpp:46, 66, 68, 215` |
| Python | `experts.py:27-40, 259-280`, the decode branch of `plan` and the `dec` handling in `listed_tile`, `fusable` and `routed`, the `expert_decode` field and flag |
| Tools | `tools/exl3_expert_sweep.py` (125 lines) |
| Tests | `test_exl3_decode_switches.py` (250 lines), `cuda/test_exl3_decode_kernels.py` (211), `cuda/test_exl3_decode_replies.py` (89), `cuda/test_glm_exl3_decode_replies.py` (103) |
| Move first | `NVCC, FakeExt, _layer, _ptxas`, which `test_exl3_prefill_switches.py:23` and `test_exl3_expert_items.py:15` import from `test_exl3_decode_switches`. Also `LAYERS, LINEAR, _inputs, _layer, _same, _scale, _trellis`, which three kernel tests import from `cuda/test_exl3_decode_kernels` |

The removal changes no served bytes or speed. It needs a GPU build and the reply tests.

**`TF_FLASHNEXT_F16_NARROW`: remove.** It served 1.00x. The code is `narrow_tile`, `Scratch.narrow`, the flag and its
plumbing through `engine.py`, `weights.load` and `exl3.load` (about 30 lines). The tests are
`test_flashnext_f16_narrow.py` (160 lines) and `cuda/test_flashnext_f16_narrow.py` (97). The tools
`exl3_prefill_bench.py` and `exl3_sweep2_bench.py` pass the flag. Three GPU reply tests load with `f16_narrow=True`,
so today they check the narrow tiles instead of the served wide ones: `test_exl3_prefill_replies.py:77`, and the
decode and sweep2 reply tests.

**`TF_EXL3_PDL`: keep for now.** It touches 108 lines across 9 files. Every EXL3 launch goes through
`tf_exl3_pdl::launch`, and `grid_wait`/`grid_launch` cost nothing without the attribute. TASKS.md's launch-gap item
plans PDL only where gaps reach 1 µs. Decide with that measurement and with patch 02's verdict, as one GPU-checked
change.

**d1 `union` and `per_question_sync`: remove (design call).** `per_question` is the default since 18 Oct. `union`
changed 1 of 200 answers, and `per_question_sync` gives the same bits at the same speed. That leaves
`lfm2/engine.py:159-184`, `HEADS` and the `TF_D1_HEAD` paragraph of `docs/d1-sidecar.md`. The tests to change are
`test_lfm2_d1.py:207` and `:238-260`.

## Kept on purpose

`gateup_epilogue_kernel` (`experts.cu:263-287`) copies `gateup_tail` inline. Calling the helper keeps the bits, but it
reorders the compiled code, so a change needs a speed check.

The GLM default tests (`test_glm_sweep_switches.py:24-49`, `test_glm_decode_kernels.py:33-50`) pin each default on
purpose, so a flip fails them loudly.
